# 诊断 Memory

Memory 自动把已完成诊断整理成可追溯的案例，为后续相似问题提供排查方向。它保存结构化业务结果，不读取或复用 SDK Session 消息，也不增加模型调用。当前 CLI、HTTP 和 Web 诊断都通过同一个 Runtime 自动使用这一能力，无需另装插件或向 Agent 注册写工具。

## 案例整理

`memory.py` 的确定性整理器从 `DiagnosisState` 中提取问题类别、症状、适用环境/服务/组件/版本/runtime、假设、验证步骤、信息缺口、下一步数据和评测不足。每个案例携带 `memory_id`、来源 run、来源 revision、配置版本和记录时间。

- 只有 `completed` 且有分析和报告的诊断进入案例库；等待、执行失败和取消不会归档。
- `confirmed` 只表示原诊断的业务结果。某条假设同时匹配报告及定位主结论、原评测通过、支持证据 ID 可追溯时，才标记 `evidence_supported` 并填写案例的 `confirmed_conclusion`；其他假设仍为 `unverified`。模型置信度不用于确认。
- `inconclusive` 案例保留待验证假设、缺口和下一步，`confirmed_conclusion` 始终为空。
- 案例不复制原始日志、完整报告或工具输出。证据 ID 仅作为来源 run 的追溯引用；自由文本再次脱敏，字段数量与长度有界，验证步骤只保存为参考数据。

详细原始证据、反证及评测内容仍从来源诊断查询，案例摘要不会替代原报告。自动整理不执行验证步骤、修复、发布或重启。

## 相似问题检索

Runtime 在首次原生诊断 turn 前检索历史案例；兼容四节点 Graph 在首次定位节点前检索。检索采用英文技术词/错误码和中文双字词的确定性词项重合，不依赖 embedding 服务。

1. 以原 run 中的 tenant ID、已选目标环境/服务（缺省时使用业务 context）做严格相等筛选；缺少值是独立范围，不是通配符。tenant 取自应用服务写入的身份上下文，现有 local 执行也支持 context 中的 tenant 标签；这不新增跨租户访问鉴权。
2. 在范围内读取最近 200 个案例；已知且非 unknown 的问题类别进一步限制候选。排除本次 run。
3. 用问题、实际表现、已取得证据和已有分析，与历史问题摘要/症状计算 Jaccard 相似度；低于 0.08 的候选舍弃。环境、类别一致本身不能产生匹配。相似度不是根因概率。
4. 按相似度、记录时间和 ID 排序，返回最多 3 个案例，整个引用列表最多 32 KiB；单个引用超出预算时跳过。

组件、版本和 runtime 是适用性提示，不是当前版本仍有相同根因的证明。Agent 必须先核对差异，并获取本次证据。Memory 只在同环境/服务内共享经验；语义检索、人工反馈和 Memory 案例管理页尚未实现。现象明确且有证据支持的案例另外生成[定位指南](diagnosis-guides.md)，支持入口确认和指南管理。

## 使用与审计

Run 查询中的公开字段以根目录[前后端契约](../../frontend-backend-contract.md)为准。后端调用方还可通过 `SQLiteCheckpointStore.get_memory(run_id)` 查询本次整理结果。

`memory_matches` 作为用户数据进入定位输入，平台提示明确其是不可信历史参考。历史 ID 不加入 `ContextAssembler.evidence()`；Graph 额外拒绝把这些 ID 冒充本次提取证据、假设支持或报告引用，除非本次输入/证据注册确实已含同一个 ID。历史匹配不改变 Graph 路由、独立评测或结论门禁。

Memory 检索结果（包括空列表）在节点开始时固定到检查点，节点输入审计记录包含同一列表；澄清、自动重试、Resume 和审批恢复不重新检索。之后新增案例不会改变已开始的诊断。

案例保存在业务 SQLite 的 `diagnosis_memories` 表中，与终态检查点和 Event 在同一事务提交。来源 run 唯一，来源 revision 防止重复或较旧结果覆盖。Schema v4 升级时一次性整理已有的有效完成报告，损坏状态跳过；不重复回填，不改变原诊断 revision 或事件。

## 验证

`tests/test_memory.py` 使用 fake runner 验证案例分类、脱敏与长度、范围隔离、类别/相似度筛选、事务回滚、数据库重开与迁移、Command 重放、原生及兼容 Graph 接入、跨进程澄清和历史证据门禁。测试不调用真实模型。
